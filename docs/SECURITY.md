# Security and safety

This page covers two different things: keeping the **repository's supply chain** trustworthy, and
keeping the **physical instrument** electrically safe.

## Part 1 — Software supply chain

The relevant risk class is OWASP Top 10:2025 **A03 — Software Supply Chain Failures**: builds that
silently pull in changed, compromised or unexpected components. What this repository does about it:

| Control | Where | Status |
|---|---|---|
| **Pinned firmware toolchain.** ESP32 core and every Arduino library pinned to exact versions *that were actually compiled* | [`firmware/Radar_V6/sketch.yaml`](../firmware/Radar_V6/sketch.yaml) (core 3.3.12 and 2.0.17 profiles; GFX 1.12.6, ILI9341 1.6.4, ST7735/ST7789 1.11.0, BusIO 1.17.4, XPT2046_Touchscreen 1.4) | done — compile records in [`validation/`](validation/) |
| **Pinned Python tooling** for the CAD, diagram, site and test scripts | [`requirements.txt`](../requirements.txt) (exact `==` versions) | done |
| **Software bill of materials (SBOM)** of the toolchain, CycloneDX 1.5 JSON | [`sbom/toolchain.cdx.json`](../sbom/toolchain.cdx.json), regenerated by `python scripts/gen_sbom.py` from the two pin files | done; attached to every release |
| **Release checksums.** Every release ZIP ships with `SHA256SUMS` | `.github/workflows/release.yml` → `scripts/make_release_zip.py` | done (runs on `v*` tags) |
| **Signed releases.** A Sigstore-signed build-provenance attestation is created for the ZIP in GitHub Actions | `actions/attest-build-provenance` in `release.yml` | done; verify with `gh attestation verify <zip> -R <owner>/ultrasonic-radar-scanner` |
| **GitHub Actions pinned by full commit hash**, with the version in a comment | every file in `.github/workflows/` | done |
| **Least-privilege tokens.** Workflows default to `contents: read`; only the jobs that need more (Pages deploy, release) get `pages`/`id-token`/`contents: write`/`attestations: write` | `.github/workflows/*.yml` | done |
| **Dependabot** for GitHub Actions, Python requirements and the desktop app's npm packages | [`.github/dependabot.yml`](../.github/dependabot.yml) | done |
| **CodeQL** code scanning for the Python helper scripts and the workflow files | `.github/workflows/codeql.yml` | done |
| **Drift checks.** CI fails if the committed STL files do not match `cad/geometry_report.json`, if the firmware pins disagree with `WIRING.md`, or if any geometry check fails | `tests/` + `.github/workflows/ci.yml` | done |
| **Pinned desktop toolchain.** Electron 44.5.1, electron-builder 26.15.3 and KaTeX 0.16.47 pinned exactly; every transitive package locked with an integrity hash in `app/package-lock.json`; CI and releases install with `npm ci` | `app/package.json`, `app/package-lock.json` | done; in the SBOM |
| **Locked-down desktop app.** Sandboxed renderer, context isolation, no Node.js and no preload bridge in the page, strict CSP, navigation limited to the bundled pages, external links handed to the system browser, every permission refused except Web Serial, DevTools off in packaged builds | `app/main.js`; checked by `tests/test_app.py` | done |
| **Firmware images** are compiled in GitHub Actions from the pinned profile; release images are covered by `SHA256SUMS` and the attestation. The Flash page loads ESP Web Tools 10.4.0 (Apache-2.0) from unpkg.com, pinned by version | `.github/workflows/pages.yml`, `release.yml`, `site/_templates/flash.html` | done |
| **Listen-only live console.** The web and desktop console never write to the serial port | `site/assets/live.js`; checked by `tests/test_app.py` | done |
| **Desktop binaries are unsigned** (no Windows Authenticode or Apple Developer ID certificate). Integrity and origin come from `SHA256SUMS` and the build-provenance attestation instead | release workflow | known limitation |
| No secrets in the repository; no network code in the firmware (no Wi-Fi, no Bluetooth use); the apps make no network requests except the web app's KaTeX font/script from the jsDelivr CDN | — | by design |

### Verifying a release yourself

```bash
sha256sum -c SHA256SUMS                                   # file integrity
gh attestation verify ultrasonic-radar-scanner-v6.0.0.zip -R <owner>/ultrasonic-radar-scanner   # provenance (same for each app file)
```

### Updating a pinned version

Change the version in `sketch.yaml` or `requirements.txt` **only after** a real build with the new
version succeeds; commit the new compile record under `docs/validation/`, re-run
`python scripts/gen_sbom.py`, and note it in `CHANGELOG.md`. Dependabot pull requests follow the
same rule: CI must be green, and firmware bumps also need a bench re-test before release.

### Reporting a vulnerability

Please use GitHub **private vulnerability reporting** (repository → *Security* → *Report a
vulnerability*) rather than a public issue. Expect an acknowledgement within 7 days. In scope: the
build scripts, workflows and anything that could make a published artifact differ from its source.

## Part 2 — Electrical safety

The V6 design has **no battery**, so the battery hazards of earlier versions are gone. What remains:

* Wire with USB **unplugged**, and check every wire against [`WIRING.md`](WIRING.md) before powering up.
* Use a **3.3 V-capable** sensor (RCWL-1601 / HC-SR04P). A 5 V-only HC-SR04's echo can damage the
  ESP32 input unless it goes through the documented divider.
* Measure P1 VIN before connecting the servo; never connect the servo to 3.3 V.
* Power from a charger or power bank rated ≥ 1 A. Unplug it if anything gets hot or smells.
* The servo is toy-grade and unguarded: keep fingers and hair away from the turning head.

## Part 3 — What this instrument is not

It is an **educational ultrasonic (sonar) instrument with a radar-style display.** It is not a
radio-frequency radar, not a safety device, and not an obstacle-avoidance or people-detection
system. It does not scan 360°, its 200 cm display range is not a verified sensing range, and the
angle shown is the commanded servo position rather than a measured one. The case carries this
label engraved on its back and the firmware shows it on the start-up screen.
